# FoodQueue — ระบบสั่งอาหารผ่าน QR สำหรับร้านชาบู/บุฟเฟ่ต์

Status: ready-for-agent

Source: `plan.md` (แผนที่อนุมัติแล้ว สำเนาเหมือนต้นฉบับทุกไบต์) — spec นี้คือข้อกำหนดเชิงพฤติกรรม ส่วน plan.md คือรายละเอียดการลงมือสร้าง; จุดที่ spec นี้ต่างจาก plan.md ให้ยึด spec นี้ (ดูหัวข้อ "ส่วนที่ต่างจาก plan.md") และหน้าจอที่ออกแบบแล้วอยู่ใน `design/` (mockup PNG) กับ `DESIGN.md`

## Problem Statement

เจ้าของร้านชาบู/บุฟเฟ่ต์ขนาดเล็ก–กลางต้องรับออเดอร์ด้วยพนักงาน จดกระดาษ และคิดเงินด้วยมือ ทำให้ออเดอร์ตกหล่น ครัวไม่รู้ว่าอะไรค้าง ลูกค้ารอนานโดยไม่รู้สถานะ พนักงานต้องคอยจับเวลา 90 นาทีของแต่ละโต๊ะ และตอนปิดบิลต้องรวมค่าบุฟเฟ่ต์ ค่าเครื่องดื่ม และค่าปรับอาหารเหลือเอง เจ้าของร้านไม่มีภาพรวมยอดขายหรือเมนูขายดีที่เชื่อถือได้

ในฐานะ portfolio full-stack ต้องแสดงให้ผู้ชมที่ไม่ได้ติดตั้งระบบเห็นได้ภายในไม่กี่คลิกว่าระบบทำงานครบวงจรแบบ real-time ทั้งฝั่งลูกค้า ครัว และเจ้าของร้าน

## Solution

ระบบเว็บที่ลูกค้าสแกน QR ซึ่งพิมพ์ให้เฉพาะรอบการนั่งของแต่ละโต๊ะ แล้วสั่งอาหารจากมือถือโดยไม่ต้องสมัครสมาชิก:

- เจ้าของร้านเปิดโต๊ะ ระบุแพ็กเกจบุฟเฟ่ต์และจำนวนผู้ใหญ่/เด็ก ระบบออก QR slip ที่ใช้ได้จนกว่าจะปิดบิล
- ลูกค้าเห็นเมนูตามระดับแพ็กเกจ สั่งเป็นรอบ ๆ ภายใต้ลิมิตกันสั่งเกิน และเห็นรายการรวมของทั้งโต๊ะที่อัปเดตเอง (ไม่เห็นสถานะรายรอบ ไม่เห็นบิล ไม่มีตัวนับถอยหลัง); เมื่อหมดเวลาการสั่งถูกปิดทันที
- ครัวเห็นออเดอร์ใหม่ทันทีบนจอ Kitchen Display และเลื่อนสถานะ Pending → Preparing → Ready (สิ้นสุดที่พร้อมเสิร์ฟ พนักงานนำไปเสิร์ฟเอง)
- เจ้าของร้านจัดการโต๊ะ (ผังโต๊ะ จำนวนที่นั่ง ย้ายโต๊ะ รวมบิล) เมนู แพ็กเกจ ออเดอร์ (แก้ไข ยกเลิก) ปรับยอดบิล รับชำระเงิน (Cash / PromptPay / Card) พิมพ์ใบแจ้งยอดและใบเสร็จ ดูสถิติยอดขาย ตั้งค่าร้าน และได้ป๊อปอัปพร้อมเสียงเมื่อมีออเดอร์ใหม่
- Demo Mode มีข้อมูลตัวอย่าง ประวัติ 30 วัน ปุ่มเข้าใช้ทันทีตาม role bot จำลองลูกค้า และหน้า split-screen 3 มุมมอง

ร้านเดียว UI ภาษาไทยอย่างเดียว mobile-first สไตล์ Modern Minimal รันในเครื่องด้วย docker compose

## User Stories

### ลูกค้า
1. ในฐานะลูกค้า ฉันต้องการสแกน QR ที่พนักงานให้แล้วเข้าหน้าสั่งอาหารได้ทันทีโดยไม่ต้องสมัครสมาชิก เพื่อให้เริ่มสั่งได้ภายในไม่กี่วินาที
2. ในฐานะลูกค้า ฉันต้องการเห็นชื่อโต๊ะและแพ็กเกจของฉันบนแบนเนอร์ร้านด้านบน เพื่อให้แน่ใจว่าสั่งถูกโต๊ะ
3. ในฐานะลูกค้า ฉันต้องการเห็นประกาศ "Last order" (เป็นข้อความ ไม่มีตัวนับเวลา) เมื่อเหลือเวลาไม่เกินที่ร้านตั้ง เพื่อไม่พลาดโอกาสสั่งรอบสุดท้าย
4. ในฐานะลูกค้า ฉันต้องการให้การตัดสินว่าหมดเวลาหรือถึง Last order ตรงกับนาฬิกาของร้านแม้นาฬิกามือถือฉันเพี้ยน เพื่อไม่ถูกปฏิเสธออเดอร์อย่างงง ๆ
5. ในฐานะลูกค้า ฉันต้องการเห็นเฉพาะเมนูบุฟเฟ่ต์ที่แพ็กเกจของฉันสั่งได้ เพื่อไม่เสียเวลาเลือกเมนูที่สั่งไม่ได้
6. ในฐานะลูกค้า ฉันต้องการเห็นเมนูที่คิดเงินแยก (เช่น เครื่องดื่ม) พร้อมราคาชัดเจน เพื่อรู้ก่อนสั่งว่าจะเสียเงินเพิ่มเท่าไร
7. ในฐานะลูกค้า ฉันต้องการเห็นป้าย "รวมในบุฟเฟ่ต์" บนเมนูบุฟเฟ่ต์ เพื่อไม่กังวลว่าจะถูกคิดเงินเพิ่ม
8. ในฐานะลูกค้า ฉันต้องการสลับหมวดหมู่ด้วยแท็บที่เลื่อนได้และติดอยู่ด้านบน เพื่อหาเมนูได้เร็วบนจอเล็ก
9. ในฐานะลูกค้า ฉันต้องการเห็นรูปเมนู (หรือตัวอักษรแทนเมื่อไม่มีรูป) เพื่อเลือกอาหารได้ง่าย
10. ในฐานะลูกค้า ฉันต้องการเห็นเมนูที่หมดเป็นสีเทาพร้อมป้าย "หมด" และกดสั่งไม่ได้ เพื่อไม่สั่งของที่ไม่มี
11. ในฐานะลูกค้า ฉันต้องการให้ป้าย "หมด" อัปเดตทันทีเมื่อร้านเปลี่ยนสถานะ เพื่อไม่ต้องรีเฟรชหน้า
12. ในฐานะลูกค้า ฉันต้องการเพิ่ม/ลดจำนวนด้วยปุ่ม +/− ที่กดง่ายด้วยนิ้วโป้ง เพื่อสั่งได้เร็ว
13. ในฐานะลูกค้า ฉันต้องการให้ปุ่ม + หยุดเมื่อถึงลิมิตต่อเมนู เพื่อรู้ว่าสั่งเพิ่มไม่ได้แล้วก่อนส่ง
14. ในฐานะลูกค้า ฉันต้องการเห็นจำนวนรวมในตะกร้าเทียบกับลิมิตต่อรอบ เพื่อวางแผนจำนวนที่จะสั่ง
15. ในฐานะลูกค้า ฉันต้องการใส่หมายเหตุต่อรายการ (เช่น ไม่เผ็ด) เพื่อให้ครัวเตรียมตามที่ต้องการ
16. ในฐานะลูกค้า ฉันต้องการให้ตะกร้ายังอยู่หากฉันรีเฟรชหรือสลับแอป เพื่อไม่ต้องเลือกใหม่
17. ในฐานะลูกค้า ฉันต้องการให้ตะกร้าแยกกันในแต่ละมือถือของคนที่โต๊ะเดียวกัน เพื่อไม่ไปทับกัน
18. ในฐานะลูกค้า ฉันต้องการกด "ส่งออเดอร์" แล้วได้ข้อความยืนยันว่าส่งแล้ว เพื่อมั่นใจว่าส่งสำเร็จ
19. ในฐานะลูกค้า ฉันต้องการให้ตะกร้าล้างหลังส่งสำเร็จ เพื่อไม่ส่งซ้ำโดยไม่ตั้งใจ
20. ในฐานะลูกค้า ฉันต้องการเห็นรายการทั้งหมดที่โต๊ะสั่งในหน้าเดียว (รวมที่เพื่อนสั่ง รวมจำนวนต่อเมนู มีหมายเหตุและรูปเล็ก ไม่แยกรอบ ไม่มีสถานะ) เพื่อรู้ว่าโต๊ะสั่งอะไรไปแล้ว
21. ในฐานะลูกค้า ฉันต้องการให้รายการของโต๊ะอัปเดตเองแบบ real-time เมื่อเพื่อนส่งออเดอร์หรือร้านแก้/ยกเลิกรายการ เพื่อไม่ต้องรีเฟรช
22. ในฐานะลูกค้า ฉันต้องการให้รายการที่ถูกยกเลิกหรือถูกนำออกหายจากรายการของโต๊ะ เพื่อไม่เข้าใจผิดว่ายังมีอาหารที่จะมา
23. ในฐานะลูกค้า ฉันต้องการข้อความชัดเจนเป็นภาษาไทยเมื่อสั่งไม่ได้ (เกินลิมิต หมดเวลา เมนูหมด เมนูไม่อยู่ในแพ็กเกจ) เพื่อรู้ว่าต้องแก้อะไร
24. ในฐานะลูกค้า ฉันต้องการเห็นข้อความ "หมดเวลาสั่งอาหาร" และปุ่มสั่งถูกปิด เมื่อเวลาหมด เพื่อไม่พยายามส่งโดยเปล่าประโยชน์
25. ในฐานะลูกค้า ฉันต้องการให้ระบบกลับมาเชื่อมต่อเองและข้อมูลถูกต้องเมื่อเน็ตหลุดแล้วกลับมา เพื่อไม่ต้องรีเฟรช
26. ในฐานะลูกค้า ฉันต้องการเห็นสถานะ "ออฟไลน์" เมื่อการเชื่อมต่อหลุด เพื่อรู้ว่าข้อมูลบนจออาจไม่ใหม่
27. ในฐานะลูกค้า ฉันต้องการหน้า "ขอบคุณที่ใช้บริการ" (ไม่แสดงยอดเงิน) เมื่อโต๊ะปิดบิลแล้ว เพื่อรู้ว่าเสร็จสิ้นและสั่งต่อไม่ได้
28. ในฐานะลูกค้า ฉันต้องการเห็น "QR ไม่ถูกต้อง" เมื่อสแกน QR ที่ไม่มีอยู่จริง เพื่อแจ้งพนักงานได้
29. ในฐานะลูกค้า ฉันต้องการให้ QR เก่าที่ถ่ายรูปไว้ใช้สั่งไม่ได้หลังโต๊ะปิดบิล เพื่อไม่มีใครสั่งอาหารเข้าบิลของคนอื่น

### ครัว
30. ในฐานะพนักงานครัว ฉันต้องการเข้าสู่ระบบด้วยบัญชีเฉพาะครัวที่เข้าได้แค่จอครัว เพื่อไม่เผลอแตะข้อมูลการเงิน
31. ในฐานะพนักงานครัว ฉันต้องการเห็นออเดอร์ใหม่ปรากฏทันทีโดยไม่ต้องรีเฟรช เพื่อทำอาหารได้เร็ว
32. ในฐานะพนักงานครัว ฉันต้องการได้ยินเสียงแจ้งเตือนสั้น ๆ เมื่อมีออเดอร์ใหม่ และปิดเสียงได้ เพื่อไม่พลาดออเดอร์ในครัวที่วุ่นวาย
33. ในฐานะพนักงานครัว ฉันต้องการเห็นการ์ดใหม่ถูกไฮไลต์ชั่วคราว เพื่อแยกออกจากการ์ดเดิม
34. ในฐานะพนักงานครัว ฉันต้องการบอร์ด 3 คอลัมน์ รอรับ / กำลังทำ / พร้อมเสิร์ฟ เพื่อเห็นงานทั้งหมดในหน้าเดียว
35. ในฐานะพนักงานครัว ฉันต้องการเห็นโต๊ะ เลขรอบ รายการ จำนวน และหมายเหตุที่เน้นให้เด่น บนการ์ดเดียว เพื่อทำตามที่ลูกค้าขอ
36. ในฐานะพนักงานครัว ฉันต้องการเห็นเวลาที่ออเดอร์รอมา และสีแดงเมื่อเกิน 10 นาที เพื่อจัดลำดับงานที่ช้า
37. ในฐานะพนักงานครัว ฉันต้องการปุ่มใหญ่ "เริ่มทำ" และ "พร้อมเสิร์ฟ" และเห็นข้อความ "รอพนักงานนำไปเสิร์ฟ" บนออเดอร์ที่พร้อมแล้ว เพื่อกดได้ง่ายบนแท็บเล็ตด้วยมือเปียก
38. ในฐานะพนักงานครัว ฉันต้องการยกเลิกออเดอร์พร้อมระบุเหตุผล (เช่น วัตถุดิบหมด) เพื่อให้ลูกค้าและเจ้าของร้านรู้สาเหตุ
39. ในฐานะพนักงานครัว ฉันต้องการให้ระบบแจ้งเมื่อออเดอร์ถูกอัปเดตจากอีกเครื่องไปแล้ว เพื่อไม่กดซ้ำจนสถานะเพี้ยน
40. ในฐานะพนักงานครัว ฉันต้องการเห็นตัวนับของแต่ละคอลัมน์และสถานะการเชื่อมต่อ เพื่อรู้ปริมาณงานและว่าหน้าจอยัง live อยู่
41. ในฐานะพนักงานครัว ฉันต้องการให้หน้าจอใช้งานได้บนแท็บเล็ตแนวนอน เพื่อติดตั้งในครัวได้จริง

### เจ้าของร้าน — โต๊ะและ session
42. ในฐานะเจ้าของร้าน ฉันต้องการเข้าสู่ระบบด้วยอีเมล/รหัสผ่าน และออกจากระบบได้ เพื่อป้องกันคนนอกเข้าหลังร้าน
43. ในฐานะเจ้าของร้าน ฉันต้องการเห็นผังโต๊ะทั้งหมดว่าใช้งานอยู่หรือว่าง (สองสถานะ ไม่มีการกะพริบ) และโต๊ะไหนมีออเดอร์รอรับ เพื่อจัดที่นั่งลูกค้าได้ทันที
44. ในฐานะเจ้าของร้าน ฉันต้องการเปิดโต๊ะโดยเลือกแพ็กเกจและจำนวนผู้ใหญ่/เด็ก เพื่อให้ค่าบุฟเฟ่ต์คิดถูกตั้งแต่ต้น
45. ในฐานะเจ้าของร้าน ฉันต้องการให้ระบบสร้าง QR เฉพาะรอบนั้นและแสดงบนจอ เพื่อให้ลูกค้าสแกนจากมือถือฉันได้
46. ในฐานะเจ้าของร้าน ฉันต้องการพิมพ์ QR slip (โต๊ะ แพ็กเกจ จำนวนคน เวลาเปิด-หมด) บนกระดาษ 80mm เพื่อวางที่โต๊ะ
47. ในฐานะเจ้าของร้าน ฉันต้องการป้องกันการเปิดโต๊ะซ้ำที่ยังมีลูกค้านั่งอยู่ เพื่อไม่ให้บิลสองใบทับกัน
48. ในฐานะเจ้าของร้าน ฉันต้องการเห็นบนโต๊ะที่ไม่ว่าง ว่าแพ็กเกจอะไร กี่คน เวลาเริ่ม–สิ้นสุด ใช้ไปแล้วกี่นาที ออเดอร์ค้างครัวกี่รอบ และยอดสะสม เพื่อดูแลโต๊ะได้ทั่วถึง
49. ในฐานะเจ้าของร้าน ฉันต้องการยกเลิกโต๊ะที่เปิดผิดโดยยังไม่มีออเดอร์ เพื่อไม่ต้องเก็บเงินที่ไม่ควรมี
50. ในฐานะเจ้าของร้าน ฉันต้องการให้การยกเลิกโต๊ะถูกปฏิเสธหากมีออเดอร์ที่ยังไม่ถูกยกเลิก เพื่อไม่ทำข้อมูลการขายหาย

### Demo Mode (ผู้ชม portfolio)
104. ในฐานะผู้ชม portfolio ฉันต้องการกดปุ่มเดียวเข้าใช้ในบทบาทเจ้าของร้านหรือครัวโดยไม่ต้องพิมพ์รหัสผ่าน เพื่อดูระบบได้ทันที
105. ในฐานะผู้ชม portfolio ฉันต้องการเปิดมุมมองลูกค้าที่เป็นโต๊ะจริงในระบบ เพื่อลองสั่งอาหารและเห็นผลฝั่งครัว
106. ในฐานะผู้ชม portfolio ฉันต้องการเห็นรายงานที่มีประวัติ 30 วันตั้งแต่เปิดครั้งแรก เพื่อประเมินหน้าสถิติได้โดยไม่ต้องรอข้อมูลสะสม
107. ในฐานะผู้ชม portfolio ฉันต้องการเห็น bot จำลองลูกค้าสั่งอาหารเอง เพื่อเห็น real-time โดยไม่ต้องลงมือเอง
108. ในฐานะผู้ชม portfolio ฉันต้องการหน้าเดียวที่แสดงลูกค้า ครัว และเจ้าของร้านเคียงกัน เพื่อเห็นข้อมูลไหลระหว่างบทบาทในคลิปหรือการเดโม
109. ในฐานะผู้พัฒนา ฉันต้องการปิด Demo Mode ด้วย config เดียว และให้ endpoint ของ demo ตอบ 404 เมื่อปิด เพื่อไม่หลุดไปใช้จริง
110. ในฐานะผู้พัฒนา ฉันต้องการให้ bot ไม่แตะโต๊ะที่คนจริงเปิดอยู่ เพื่อไม่รบกวนการเดโมของฉัน
111. ในฐานะผู้พัฒนา ฉันต้องการรันทั้งระบบด้วยคำสั่งเดียว (docker compose) บนเครื่อง เพื่อสาธิตและพัฒนาได้ง่าย

## Implementation Decisions

### สถาปัตยกรรม
- Backend: ASP.NET Core 10 เป็น modular monolith แบบ vertical slice ด้วย Minimal APIs, โปรเจกต์ API เดียว + โปรเจกต์ทดสอบเดียว แบ่งโมดูลตามฟีเจอร์ (Auth, Tables, Packages, Menu, Sessions, Orders, Billing, Reports, Settings, Demo, Customer) ไม่ใช้ MediatR และไม่แบ่งเลเยอร์ Clean Architecture
- Persistence: PostgreSQL + EF Core, migration ตัวเดียวชื่อ Initial, apply อัตโนมัติตอนสตาร์ท เหมาะกับการรัน local; เงินเป็น decimal(10,2), เวลาเป็น UTC timestamptz, enum เก็บเป็น string
- Frontend: Next.js App Router + TypeScript + Tailwind + shadcn/ui + TanStack Query + SignalR client + Recharts; UI ภาษาไทยอย่างเดียว ฟอนต์ IBM Plex Sans Thai
- Single origin: Caddy เป็น reverse proxy ให้ web, `/api` และ `/hubs` อยู่ origin เดียว (`http://localhost:8080`) เพื่อให้ cookie auth และ WebSocket ทำงานโดยไม่ต้องมี CORS หรือ Next proxy WebSocket (ควรบันทึกเป็น ADR)
- Auth: ASP.NET Identity + cookie (ไม่ใช้ JWT), 401/403 ตอบเป็น status ไม่ redirect; role `Owner` และ `Kitchen`; policy `OwnerOnly` และ `KitchenAccess` (Owner หรือ Kitchen); ลูกค้าไม่มีบัญชี ใช้ Session Token เป็นตัวระบุเท่านั้น
- ร้านเดียว: ไม่มี tenant/RestaurantId; ข้อมูลร้านเป็น singleton settings

### โมเดลโดเมน
- **Table**: โต๊ะจริง ชื่อไม่ซ้ำ, จำนวนที่นั่ง 1–20, โซน (ข้อความสั้น เช่น A, B), soft-disable ด้วยสถานะ active; ปิดใช้งานได้เฉพาะโต๊ะที่ไม่มี session Open
- **Package**: ชื่อ, `Rank` (ไม่ซ้ำ), ราคาผู้ใหญ่, ราคาเด็ก, ระยะเวลา (นาที), active; ไม่มีการลบ
- **Category / MenuItem**: MenuItem มี `Kind` = Buffet หรือ AlaCarte; Buffet ต้องมี MinPackageRank และราคา 0; AlaCarte ต้องไม่มี MinPackageRank และราคา > 0; มีสถานะ `IsAvailable` (ของหมดชั่วคราว) แยกจาก `IsActive`; ไม่มี option group มีแค่หมายเหตุอิสระต่อรายการ (≤100 ตัวอักษร); น้ำซุปเป็น Buffet Item ในหมวดของมัน
- **Table Session** (_Avoid_: visit, check): หนึ่งรอบการนั่ง = หนึ่งบิล; สถานะ Open → Paid หรือ Voided; มี Session Token แบบสุ่มเดาไม่ได้ (256 บิต, base64url 43 ตัวอักษร); snapshot ชื่อ/ราคา/rank ของแพ็กเกจ ณ ตอนเปิด; `EndsAt = OpenedAt + DurationMinutes` ต่อเวลาไม่ได้ (เมื่อถึง EndsAt การสั่งปิด แต่ session ยังเปิดรอชำระ); โต๊ะหนึ่งมี session Open ได้ทีละหนึ่ง (บังคับด้วย partial unique index ในฐานข้อมูล); ย้ายไปโต๊ะอื่นได้โดย token เดิม; หลาย session ที่ Open รวมเข้าบิลของ session หลักได้ (ดูกฎการรวมบิล)
- **Order**: การส่งหนึ่งรอบ มีเลขรอบรันต่อ session และสถานะเดียวทั้งออเดอร์: Pending → Preparing → Ready (สถานะสุดท้ายในระบบ พนักงานนำไปเสิร์ฟเอง ไม่มีขั้น Served) กับ Cancelled (ต้องมีเหตุผล) ซึ่ง Kitchen/Owner ยกเลิกได้จากสามสถานะแรกเท่านั้น; ลูกค้ายกเลิกไม่ได้; Owner ลดจำนวน/นำรายการออกจากออเดอร์ที่ Pending/Preparing ได้ (กฎแก้ออเดอร์); OrderItem snapshot ชื่อ ชนิด ราคา
- **Bill Adjustment**: รายการปรับยอดบวก/ลบพร้อมเหตุผลของ session ที่ Open
- **Payment**: หนึ่ง session หนึ่ง payment; วิธีจ่าย Cash / PromptPay / Card; เก็บยอดแยกส่วนที่คำนวณ ณ ตอนจ่าย; เลขใบเสร็จรูปแบบ `R` + วันที่ (เวลาไทย) + `-` + ลำดับ 6 หลัก จาก sequence ของฐานข้อมูล ไม่ซ้ำ
- **Settings**: ชื่อร้าน ที่อยู่ โทร เลขผู้เสียภาษี PromptPay ID, ภาพแบนเนอร์ร้าน (ไม่บังคับ), Service charge %, VAT % (0–30, เริ่ม 0), ลิมิตต่อเมนูต่อรอบ (เริ่ม 5), ลิมิตรวมต่อรอบ (เริ่ม 20), นาทีเตือน Last order (เริ่ม 15); ลิมิตตั้งได้ 1–99

### กฎธุรกิจที่ต้องตรงตามนี้
- เมนูที่ลูกค้าเห็น/สั่งได้: Buffet Item ที่ `MinPackageRank <= rank ของ session` + AlaCarte ทุกรายการ เฉพาะที่ active
- ตรวจการสั่งตามลำดับนี้: session Open → ยังไม่เลย EndsAt → รายการไม่ว่าง → จำนวนต่อเมนู (รวมบรรทัดที่ซ้ำเมนูเดียวกัน) ≤ ลิมิต → จำนวนรวม ≤ ลิมิต → เมนูมีอยู่และ active → IsAvailable → เมนู Buffet อยู่ในสิทธิ์แพ็กเกจ; ตรวจที่ server เสมอ (client ตรวจซ้ำเพื่อ UX)
- เลขรอบออเดอร์ = max+1 ใน transaction เดียว, retry หนึ่งครั้งเมื่อชน unique
- การเลื่อนสถานะต้องเป็น conditional update จากสถานะก่อนหน้าที่คาดไว้ ถ้าไม่มีแถวถูกอัปเดตให้ตอบ `INVALID_STATUS_TRANSITION` — กันครัวสองเครื่องกดพร้อมกัน
- ตัวคำนวณบิลเป็นฟังก์ชันบริสุทธิ์จุดเดียว ใช้ร่วมกันทุกที่ (บิลลูกค้า บิลเจ้าของ การจ่ายเงิน ข้อมูลพิมพ์):
  - ค่าบุฟเฟ่ต์ = ผู้ใหญ่×ราคาผู้ใหญ่ที่ snapshot + เด็ก×ราคาเด็กที่ snapshot
  - ค่า à la carte = Σ ราคา×จำนวน ของออเดอร์ที่ไม่ใช่ Cancelled
  - subtotal = ค่าบุฟเฟ่ต์ + à la carte + Σ ปรับยอด
  - service = ปัด 2 ตำแหน่ง (AwayFromZero) ของ subtotal×SC%
  - vat = ปัด 2 ตำแหน่ง (AwayFromZero) ของ (subtotal+service)×VAT%
  - total = subtotal + service + vat
- การปิดบิล: session ต้อง Open (มิฉะนั้น `ALREADY_PAID`); ต้องไม่มีออเดอร์ Pending/Preparing (`ORDERS_IN_PROGRESS`; ออเดอร์ Ready ไม่ขวางการปิดบิล); Cash ต้องรับเงิน ≥ total (`INSUFFICIENT_AMOUNT`) วิธีอื่นถือว่ารับเท่ากับ total; สำเร็จแล้ว session เป็น Paid และ token ใช้สั่งไม่ได้
- การยกเลิกโต๊ะ (void) ทำได้เฉพาะ session Open ที่ไม่มีออเดอร์ที่ไม่ถูกยกเลิก (`SESSION_HAS_ORDERS`)
- ปรับยอดทำได้เฉพาะ session Open และห้ามทำให้ subtotal ติดลบ (`NEGATIVE_SUBTOTAL`)
- ไม่มีการต่อเวลา: เมื่อเลย EndsAt การสั่งถูกปิด (`SESSION_EXPIRED`) แต่บิลยังปรับยอดและชำระได้; ไม่มีค่าปรับเกินเวลาอัตโนมัติ; Last order (เหลือเวลา ≤ ค่าที่ตั้ง) เป็นข้อความเตือนเท่านั้น ไม่ปิดการสั่ง
- แก้ออเดอร์ (Owner): เฉพาะออเดอร์ Pending/Preparing ของ session Open; ลดจำนวนหรือนำรายการออกเท่านั้น (เพิ่มรายการหรือจำนวนไม่ได้); ต้องระบุเหตุผล; นำออกครบทุกรายการ = ยกเลิกทั้งออเดอร์; สถานะออเดอร์ไม่เปลี่ยน; ยอดบิลคำนวณใหม่ทันที; ออเดอร์ที่ไม่อยู่ในสถานะที่แก้ได้ → `ORDER_NOT_EDITABLE`
- ย้ายโต๊ะ (Owner): session Open ไปโต๊ะ active ที่ไม่มี session Open เท่านั้น (มิฉะนั้น `TABLE_OCCUPIED`); ย้ายทั้ง session (ออเดอร์ บิล รายการปรับยอด เวลา) โดย token และ QR เดิมไม่เปลี่ยน; โต๊ะเดิมว่างทันที
- รวมบิล (Owner): เลือก session หลักหนึ่งอัน และ session Open อื่นเข้ามารวมได้ แม้ครัวยังทำออเดอร์ไม่เสร็จ; session ที่ถูกรวมยังสั่งผ่าน QR เดิมได้ตาม EndsAt ของตัวเอง และออเดอร์ใหม่เข้าบิลรวม; subtotal ของบิลรวม = ผลรวม subtotal ของทุก session แล้วคิด SC/VAT ครั้งเดียวจากผลรวม; ชำระครั้งเดียวที่ session หลัก ใบเสร็จใบเดียว; เมื่อชำระแล้วทุก session ที่รวมเป็น Paid และ token ทุกอันสั่งไม่ได้ โต๊ะทั้งหมดว่าง; ยกเลิกการรวมไม่ได้
- PromptPay QR สร้างฝั่ง frontend จาก PromptPay ID กับยอดรวม; ถ้ายังไม่ตั้ง ID ให้ปิดตัวเลือกและแจ้งข้อความ

### สัญญา API (สรุป)
- Auth: login (204), logout, me
- Owner: CRUD โต๊ะ (ชื่อ ที่นั่ง โซน)/แพ็กเกจ/หมวด/เมนู, สลับ availability, อัปโหลดรูปเมนูและแบนเนอร์ร้าน, settings; overview ของโต๊ะ (Kitchen เข้าได้) คืนเวลาเริ่ม/สิ้นสุดและนาทีที่ใช้ไป
- Sessions: เปิด (คืน QR URL), ดูรายละเอียด/รายการ/ประวัติ, ปรับยอด (เพิ่ม/ลบ), void, ย้ายโต๊ะ, รวมบิล, payment, ข้อมูลสำหรับพิมพ์
- Customer (ไม่ต้อง auth ใช้ token): ข้อมูล session (ชื่อโต๊ะ แพ็กเกจ จำนวนคน แบนเนอร์ร้าน และเวลาเซิร์ฟเวอร์เพื่อชดเชยนาฬิกา), เมนู, รายการรวมของโต๊ะ (ไม่มีสถานะ ไม่มียอดบิล), สั่งอาหาร
- Kitchen: รายการออเดอร์ตามสถานะ/วัน, เลื่อนสถานะ, ยกเลิกพร้อมเหตุผล; Owner: แก้รายการในออเดอร์
- Reports: summary ตามช่วง today/7d/30d
- Demo: status (ไม่ต้อง auth), login ตาม role, customer-session
- ข้อผิดพลาดเป็น ProblemDetails พร้อม field `code` คงที่ และ `message` ภาษาไทยที่แสดงต่อผู้ใช้ได้ตรง ๆ; รายการ code: `SESSION_NOT_FOUND`, `SESSION_CLOSED`, `SESSION_EXPIRED`, `TABLE_OCCUPIED`, `ITEM_NOT_FOUND`, `ITEM_UNAVAILABLE`, `ITEM_NOT_IN_PACKAGE`, `QTY_LIMIT_EXCEEDED`, `ORDER_ITEMS_LIMIT_EXCEEDED`, `EMPTY_ORDER`, `INVALID_STATUS_TRANSITION`, `ORDER_NOT_EDITABLE`, `ORDERS_IN_PROGRESS`, `NEGATIVE_SUBTOTAL`, `SESSION_HAS_ORDERS`, `ALREADY_PAID`, `INSUFFICIENT_AMOUNT`, `VALIDATION_FAILED`

### Realtime (SignalR, hub เดียว)
- Groups: kitchen, owner, session ต่อรอบ, menu
- ลูกค้าเชื่อมต่อด้วย token ที่ต้องเป็น session Open เท่านั้น มิฉะนั้นตัดการเชื่อมต่อ; เข้าได้เฉพาะ group ของ session ตัวเองและ menu — ห้ามเห็นข้อมูลโต๊ะอื่น
- Staff เข้า group ตาม role (Owner: owner+kitchen+menu, Kitchen: kitchen+menu)
- Events: `orderCreated` (kitchen/owner/session), `orderStatusChanged` (kitchen/owner เท่านั้น — ลูกค้าไม่เห็นสถานะ), `orderEdited` (kitchen/owner/session เมื่อแก้หรือยกเลิกรายการ), `sessionChanged` (owner/session เมื่อย้าย รวม หรือปรับยอด), `menuItemChanged` (menu), `sessionClosed` (session/owner)
- ส่ง event หลังบันทึกฐานข้อมูลสำเร็จเท่านั้น; เมื่อ reconnect client ต้อง refetch ข้อมูลทั้งหมดและแสดงสถานะออฟไลน์ระหว่างที่หลุด

### Frontend
- เส้นทาง: หน้าลูกค้าตาม token, ครัว, owner (ภาพรวม/โต๊ะ/ออเดอร์/เมนู/แพ็กเกจ/รายงาน/ตั้งค่า/ประวัติ/หน้ารายละเอียด session), หน้าพิมพ์ 3 แบบ (ใบแจ้งยอด ใบเสร็จ QR slip), login, demo split-screen
- หน้าพิมพ์ใช้ browser print กระดาษ 80mm ไม่มี driver พิเศษ ไม่มี kitchen ticket; ใบเสร็จพิมพ์ได้เฉพาะ session ที่ Paid
- ไม่มีตัวนับถอยหลังบนจอใด: staff เห็นเวลาเริ่ม–สิ้นสุดและนาทีที่ใช้ไป ลูกค้าเห็นเฉพาะประกาศ Last order และสถานะหมดเวลา; การตัดสินทั้งหมดอิงเวลาเซิร์ฟเวอร์ปรับ offset และไม่เรียกเวลาปัจจุบันระหว่าง render
- สีสถานะ: Pending amber, Preparing blue, Ready green, Cancelled red และต้องผ่านคอนทราสต์ WCAG AA; ผังโต๊ะมีสองสถานะ (ใช้งานอยู่ / ว่าง) ไม่มีแอนิเมชัน
- ป๊อปอัปออเดอร์ใหม่ (Owner ทุกหน้า): แสดงโต๊ะ เลขรอบ สรุป รายการที่ขยายดูได้ ตัวบอกเสียงพร้อมปุ่มปิดเสียง และปุ่ม "ไว้ก่อน" / "ไปหน้าออเดอร์" (นำทางไปคิวออเดอร์ ไม่เริ่มทำที่ป๊อปอัป)
- Auth guard: ไม่ล็อกอิน → login; Kitchen เข้า owner ไม่ได้ → redirect ไปครัว
- ตะกร้าเก็บในเครื่องลูกค้า (ต่อ token) ส่วนรายการออเดอร์/บิลใช้ร่วมกันทั้งโต๊ะผ่านเซิร์ฟเวอร์

### Demo Mode
- เปิด/ปิดด้วย config เดียว; เมื่อปิด endpoint ของ demo ตอบ 404 และไม่มี seed/bot
- Seed แบบกำหนดซ้ำได้ (random seed คงที่) เมื่อฐานข้อมูลว่าง: ผู้ใช้ owner/kitchen demo, ร้านชาบูตัวอย่าง (SC 10%, VAT 7%, PromptPay ตัวอย่าง), โต๊ะ 12 โต๊ะ (โซน A และ B ที่นั่ง 4 ยกเว้น B3 6 ที่นั่ง รวม 50), แพ็กเกจ 3 ระดับ, เมนูประมาณ 40 รายการใน 8 หมวด, ประวัติ 30 วันย้อนหลัง (ไม่รวมวันนี้) วันละ 20–45 บิล เวลา 11:00–21:30 และสัดส่วนวิธีจ่ายประมาณ Cash 40/PromptPay 45/Card 15 มีรายการปรับยอดประมาณ 10% ของบิล
- Bot: วนทุก 20–40 วินาที ดูแลให้มี session ของ bot เปิดอย่างน้อย 3 โต๊ะ สั่งอาหาร 2–6 รายการ เลื่อนสถานะออเดอร์ที่ค้างเกิน 120 วินาที และจ่ายเงินสดให้ session ที่หมดเวลาและไม่มีออเดอร์ค้าง; ต้องเรียกผ่านบริการชุดเดียวกับที่ endpoint ใช้ (ไม่เขียนฐานข้อมูลตรง) เพื่อให้กฎและ event เหมือนของจริง; แตะเฉพาะ session ที่ถูกทำเครื่องหมายว่าเป็นของ bot; error ในรอบหนึ่งต้อง log แล้วทำรอบถัดไปต่อ
- ไม่มี auto-reset ข้อมูล
- ตรรกะการสั่ง การเลื่อนสถานะ และการชำระเงิน ต้องอยู่ในบริการที่ใช้ร่วมกัน เพื่อให้ bot และ API เป็นพฤติกรรมเดียวกัน

## Testing Decisions

### Seam ที่เสนอ (ขอให้ผู้ใช้ยืนยัน)
เลือก seam ที่สูงสุดที่ทำได้ และให้มีน้อยที่สุด — เสนอ 2 seam:
1. **HTTP + SignalR ของแอป backend จริงบนฐานข้อมูล Postgres จริง** (Testcontainers + in-process app host) ครอบคลุมกฎธุรกิจทั้งหมด รวมการคำนวณบิล/การปัดเศษ ซึ่งทดสอบผ่านผลลัพธ์ของ API บิล/การจ่าย ไม่แยก unit test ของตัวคำนวณ (ต่างจากร่างใน plan.md ที่เสนอ unit test แยก — spec นี้ยึด seam เดียวกันเพื่อไม่เพิ่ม seam)
2. **เบราว์เซอร์ end-to-end 1 flow** (Playwright) บน stack จริงที่เปิด demo เพื่อพิสูจน์ว่า UI, Caddy, cookie และ SignalR ทำงานรวมกันได้

### หลักการ
- ทดสอบเฉพาะพฤติกรรมภายนอก (คำขอ → สถานะ HTTP, `code`, ข้อมูลที่คืน, event ที่ส่ง, สถานะในฐานข้อมูลที่ผู้ใช้สังเกตได้) ไม่ทดสอบโครงสร้างภายใน ชื่อคลาส หรือการ wiring
- ทุกเทสต์ต้อง deterministic และแยกกัน; ตั้งค่าเวลาที่หมดผ่านข้อมูล (เช่น EndsAt ในอดีต) ไม่ใช่ sleep; ปิด Demo ในเทสต์ backend และ seed เฉพาะที่แต่ละเคสต้องใช้

### สิ่งที่ต้องมีเทสต์ (seam 1)
- การสั่ง: เมนู rank สูงกว่าแพ็กเกจ → `ITEM_NOT_IN_PACKAGE`; เกินลิมิตต่อเมนู (รวมบรรทัดซ้ำเมนูเดียวกัน) → `QTY_LIMIT_EXCEEDED`; เกินลิมิตรวม → `ORDER_ITEMS_LIMIT_EXCEEDED`; เมนูหมด → `ITEM_UNAVAILABLE`; เลย EndsAt → `SESSION_EXPIRED`; session ที่ Paid → `SESSION_CLOSED`; ออเดอร์ว่าง → `EMPTY_ORDER`; สั่งสำเร็จสองรอบได้เลขรอบ 1 และ 2
- เวิร์กโฟลว์: ข้ามขั้น Pending→Ready ถูกปฏิเสธ; เลื่อนต่อจาก Ready ไม่ได้; ยกเลิกออเดอร์ที่ Cancelled แล้วถูกปฏิเสธ; ยกเลิกต้องมีเหตุผล; ส่งการเลื่อนสถานะพร้อมกันสองคำขอ → สำเร็จหนึ่ง ปฏิเสธหนึ่ง
- บิล: ค่าบุฟเฟ่ต์ผู้ใหญ่+เด็กตามราคา snapshot (แก้ราคาแพ็กเกจทีหลังไม่กระทบ); ออเดอร์ยกเลิกไม่นับ; ปรับยอดติดลบ; การปัด SC/VAT (ตัวอย่าง subtotal 1000.05 กับ SC 10% ได้ service 100.01); ปรับยอดจนติดลบ → `NEGATIVE_SUBTOTAL`
- session และการชำระ: เปิดโต๊ะซ้ำ → `TABLE_OCCUPIED`; จ่ายขณะมีออเดอร์ค้าง → `ORDERS_IN_PROGRESS`; Cash ไม่พอ → `INSUFFICIENT_AMOUNT`; จ่ายซ้ำ → `ALREADY_PAID`; จ่ายสำเร็จได้เลขใบเสร็จตามรูปแบบและ token ใช้สั่งไม่ได้อีก; void ที่มีออเดอร์ → `SESSION_HAS_ORDERS`
- เวลา: เลย EndsAt แล้วสั่งไม่ได้ (`SESSION_EXPIRED`) แต่ปรับยอดและชำระได้; ไม่มีเส้นทางต่อเวลา; ปิดบิลได้เมื่อเหลือแต่ออเดอร์ Ready แต่ปิดไม่ได้เมื่อมี Pending/Preparing
- สิทธิ์: ไม่ล็อกอิน → 401; Kitchen เรียก settings/payment/reports → 403; ลูกค้าเชื่อม hub ด้วย token ที่ไม่ถูกต้องหรือ session ที่ปิดแล้วไม่ได้ และไม่ได้รับ event ของโต๊ะอื่น
- Realtime: ออเดอร์ใหม่ส่ง `orderCreated` ถึงครัวและ session ที่ถูกต้อง; เปลี่ยนสถานะส่ง `orderStatusChanged` ถึงครัวและ owner เท่านั้น (ลูกค้าไม่ได้รับ); แก้/ยกเลิกรายการส่ง `orderEdited` รวมถึง session; สลับเมนูหมดส่ง `menuItemChanged`
- รายงาน: นับเฉพาะบิลที่ Paid; ไม่นับออเดอร์ยกเลิกใน Top 10; ขอบเขตวันตามเวลาไทย (บิลเวลาใกล้เที่ยงคืน); `avgPerGuest` เป็น 0 เมื่อไม่มีลูกค้า
- Demo: endpoint ตอบ 404 เมื่อปิด; seed ซ้ำได้และ idempotent; bot เรียกใช้ผ่านบริการชุดเดียวกันและไม่แตะ session ที่ไม่ใช่ของ bot
- แก้ออเดอร์: ลดจำนวน/นำออกได้เฉพาะ Pending/Preparing และบิลคำนวณใหม่; เพิ่มจำนวนถูกปฏิเสธ; ไม่ใส่เหตุผลถูกปฏิเสธ; Ready/Cancelled → `ORDER_NOT_EDITABLE`
- ย้ายโต๊ะ: ไปโต๊ะที่มี session Open → `TABLE_OCCUPIED`; ย้ายสำเร็จแล้ว token เดิมยังสั่งได้ โต๊ะเดิมว่าง ออเดอร์/บิล/เวลาตามไปครบ
- รวมบิล: ยอดรวมตรงตัวอย่างใน mockup (subtotal 913.00 + 1,096.00 = 2,009.00; service 200.90; vat 154.69; total 2,364.59); ชำระครั้งเดียวทำให้ทุก session เป็น Paid ใบเสร็จใบเดียว; session ที่รวมแล้วยังสั่งผ่าน token เดิมได้จนกว่าจะชำระ
- โต๊ะ: ที่นั่งนอก 1–20 → `VALIDATION_FAILED`; ปิดใช้งานโต๊ะที่มี session Open ไม่ได้; ชื่อซ้ำไม่ได้

### เทสต์ end-to-end (seam 2)
Demo-login เป็น Owner → เปิดโต๊ะว่าง → ลูกค้า (context เบราว์เซอร์ใหม่) เปิด QR URL สั่งหมูสามชั้น ×2 และชาไทย ×1 → การ์ดโผล่ใน "รอรับ" ของจอครัวภายใน 5 วินาที → เลื่อนจน "พร้อมเสิร์ฟ" → หน้า "ออเดอร์" ของลูกค้าแสดงรายการที่สั่ง (ไม่มีสถานะ) → Owner รับชำระเงินสด → หน้าลูกค้าแสดง "ขอบคุณที่ใช้บริการ"; และตรวจ viewport 390×844 ว่าไม่มี horizontal scroll

## Out of Scope

- หลายร้าน / multi-tenant / สมัครร้านใหม่
- บทบาท Staff หน้าร้าน (มีแค่ Owner และ Kitchen)
- Payment gateway จริง (Stripe/Omise ฯลฯ) และการยืนยันการโอน PromptPay อัตโนมัติ — บันทึกการรับเงินด้วยมือเท่านั้น
- ลูกค้ายกเลิกออเดอร์เอง ปุ่มเรียกพนักงาน ปุ่มขอเช็คบิล
- ตะกร้าร่วมกันแบบ real-time ระหว่างมือถือหลายเครื่อง
- Option group ของเมนู (ระดับความเผ็ด ท็อปปิ้ง ขนาด)
- ค่าปรับอาหารเหลือหรือค่าเกินเวลาแบบคำนวณอัตโนมัติ (ทำเป็นรายการปรับยอดด้วยมือเท่านั้น)
- แยกบิล จ่ายทีละออเดอร์ และการยกเลิกการรวมบิล
- ต่อเวลาโต๊ะ (เมื่อหมดเวลาคือปิดการสั่ง)
- ลูกค้าดูบิล ยอดรวม หรือสถานะรายรอบ และตัวนับถอยหลังบนทุกจอ
- ขั้น "เสิร์ฟแล้ว" ในระบบ (Ready คือสถานะสุดท้าย)
- เวลารอระหว่างรอบสั่ง
- Kitchen ticket (ใบสั่งครัว) และการสั่งงานเครื่องพิมพ์ thermal โดยตรง — ใช้ browser print เท่านั้น
- สต็อก/วัตถุดิบ, สมาชิก/สะสมแต้ม, โปรโมชั่น/คูปอง
- การส่งออกรายงาน CSV
- หลายภาษา (UI ไทยอย่างเดียว)
- การ deploy ขึ้นอินเทอร์เน็ต (รัน local ด้วย docker compose เท่านั้น), HTTPS, auto-reset ข้อมูล demo
- Push notification, PWA/offline

## ส่วนที่ต่างจาก plan.md

`plan.md` เป็นสำเนาแผนที่อนุมัติก่อนออกแบบหน้าจอ และไม่ถูกแก้ไข ส่วนต่อไปนี้ spec นี้ยึดตามหน้าจอที่ออกแบบแล้ว (`design/`) และคำตัดสินของผู้ใช้:

- ไม่มีนับถอยหลังบนจอใด; หมดเวลา = ปิดการสั่งทันที; ไม่มีการต่อเวลา (plan: ต่อเวลา 15/30/60)
- ลูกค้าไม่เห็นบิล ยอดรวม สถานะรายรอบ หรือเลขรอบ; เห็นรายการรวมของโต๊ะ (plan: บิลและสถานะ real-time)
- สถานะออเดอร์สิ้นสุดที่ Ready; ไม่มี Served; การปิดบิลถูกขวางเฉพาะ Pending/Preparing (plan: Pending/Preparing/Ready ต้อง Served ก่อนจ่าย)
- เพิ่มในขอบเขต: แก้ออเดอร์ ย้ายโต๊ะ รวมบิล จำนวนที่นั่งและโซนของโต๊ะ แบนเนอร์ร้าน ป๊อปอัปออเดอร์ใหม่ (plan: ย้าย/รวมโต๊ะอยู่นอกขอบเขต)
- ผังโต๊ะสองสถานะไม่มีการกะพริบ; การกะพริบ (pulse) ใช้เฉพาะการ์ดออเดอร์ใหม่ในคิวและจอครัว

## Further Notes

- QR ในระบบนี้ผูกกับ session ไม่ใช่ตัวโต๊ะ: ผู้ใช้ตอบว่า "พิมพ์ slip" แต่ไม่ได้ติ๊ก QR slip ในรายการพิมพ์ จึงรวม QR slip ไว้เป็นเอกสารพิมพ์ที่สาม (ใบแจ้งยอด ใบเสร็จ QR slip) โปรดยืนยัน
- ถ้าจะสแกน QR ด้วยมือถือจริง ต้องตั้ง base URL สาธารณะของ QR เป็น IP ใน LAN ไม่ใช่ localhost
- Plan ที่อนุมัติแล้ว (plan.md) มีรายการขั้นตอนลงมือสร้าง โครงสร้างโฟลเดอร์ เวอร์ชันแพ็กเกจ ตัวเลขข้อมูล seed ที่ละเอียดกว่า และแผนสำรองเมื่อเครื่องมือบางตัวใช้ไม่ได้
- สมมติฐานที่ spec ตั้งเองเมื่อรวมกับ mockup (ยืนยันกับผู้ใช้ได้ภายหลัง): ภาพแบนเนอร์ใช้ข้อจำกัดไฟล์เดียวกับรูปเมนู; ตำแหน่งโต๊ะบนผังจัดตามโซนและลำดับ ไม่มีการลากวาง; ในรายงาน บิลรวมนับเป็นหนึ่งบิล จำนวนลูกค้ารวมทุก session และแพ็กเกจนับตาม session หลัก; ออเดอร์ที่ Ready ยังยกเลิกได้ (ตามเมนูบนการ์ดครัว) แต่แก้รายการไม่ได้
- `o13-settings` และ `c5-states` ยังมี Last order ตามที่คงไว้ (ตัดสินใจเก็บ); mockup ไม่มีปุ่ม "ต่อเวลา" และไม่มี "เกินเวลา" แล้ว
- Spec นี้เผยแพร่เป็นไฟล์ Markdown ในเครื่องเพราะ repo ไม่มี git remote — ไม่มีการสร้าง remote
