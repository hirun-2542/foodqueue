# 27: E2E หนึ่ง flow, วิวพอร์ตมือถือ และคุณภาพรวม

Status: ready-for-agent

Source: `../spec.md` (user stories 103) และ `../plan.md` (Step 17, Verification); ถ้า spec กับ plan ขัดกัน ให้ยึด spec; หน้าจอที่ออกแบบแล้ว: frame ทุกเฟรมใน design/out เทียบกับหน้าที่สร้าง (ตรวจเฉพาะที่ ticket ก่อนหน้าเปิดทำงานแล้ว) ใน `../../design/out/`

## What to build

มีเทสต์ end-to-end หนึ่ง flow (seam 2) ที่พิสูจน์ว่า UI, Caddy, cookie และ SignalR ทำงานรวมกันบน stack จริงที่เปิด demo และตรวจรวมทั้งระบบตามข้อกำหนด UI: ภาษาไทยอ่านง่าย สีสถานะผ่านคอนทราสต์ WCAG AA ปุ่มกดสบายบนมือถือ เคารพ `prefers-reduced-motion`

## Blocked by

15 ป๊อปอัปออเดอร์ใหม่พร้อมเสียงสำหรับเจ้าของร้านทุกหน้า, 17 แก้ออเดอร์, 19 ชำระ PromptPay, 20 พิมพ์ QR slip ใบแจ้งยอด ใบเสร็จ และประวัติการชำระ/พิมพ์ซ้ำ, 21 ย้ายโต๊ะ, 22 รวมบิลหลายโต๊ะ ชำระครั้งเดียว, 26 หน้า split-screen ลูกค้า ครัว เจ้าของร้านเคียงกัน

## Acceptance criteria

- [ ] Playwright: Demo-login Owner → เปิดโต๊ะว่าง → ลูกค้า (browser context ใหม่) เปิด QR URL สั่งหมูสามชั้น ×2 และชาไทย ×1 → การ์ดโผล่ใน "รอรับ" ของจอครัวภายใน 5 วินาที → เลื่อนจน "พร้อมเสิร์ฟ" → หน้าออเดอร์ของลูกค้าแสดงรายการที่สั่ง (ไม่มีสถานะ) → Owner รับชำระเงินสด → หน้าลูกค้าแสดง "ขอบคุณที่ใช้บริการ"
- [ ] วิวพอร์ต 390×844 ของหน้าลูกค้าไม่มี horizontal scroll
- [ ] สีสถานะ Pending/Preparing/Ready/Cancelled ผ่านคอนทราสต์ AA (ตรวจด้วยเครื่องมือ ไม่ใช่ด้วยสายตา); ปุ่มสำคัญบนมือถือขนาดแตะได้สบาย; pulse หยุดเมื่อ `prefers-reduced-motion`
- [ ] ชุดเทสต์ทั้งหมด (seam 1 + seam 2) ผ่านจากเครื่องว่างด้วยคำสั่งที่บันทึกใน README; รายงานตัวเลขผลจริง
- [ ] สร้างครบทุกชั้นที่ slice นี้แตะ (schema/API/UI) พร้อมเทสต์ seam 1 ตามหัวข้อ Testing Decisions ของ spec และ smoke run บน stack จริง (`docker compose up`) ที่เห็นพฤติกรรมของ ticket นี้ด้วยตา; โมเดลที่เพิ่มเข้า migration `Initial` ตัวเดียว (ดู ticket 01)
